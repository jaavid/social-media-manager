# فضای کاری و دسترسی

فضای کاری ظرف حساب‌ها، پست‌ها، آمار، پیام‌ها و تنظیمات یک برند است. مالک، اعضا و آژانس فقط در محدودهٔ مجاز خود کار می‌کنند. مجوز backend مرجع نهایی است؛ نمایش یک دکمه در UI مجوز ایجاد نمی‌کند.

## سازمان و مرز tenant

هر فضای کاری یک `Organization` اجباری دارد. سازمان مالکیت، عضویت و سیاست مشترک را نگه می‌دارد؛ `Agency` شریک خدماتی است و رابطهٔ مدیریت آن مالکیت سازمان را تغییر نمی‌دهد. سیاست `requires_approval` سازمان حداقل اجباری برای انتشار و زمان‌بندی تمام فضاهای کاری آن است؛ کاربر، فضای کاری یا حساب نمی‌تواند آن را لغو کند.

مالک سازمان (`owner_user`) حق مدیریت سازمان، اعضا و ساخت فضای کاری در آن را دارد. عضو فعال سازمان فقط به اطلاعات سازمان دسترسی دارد؛ مالکیت یا عضویت سازمان به‌تنهایی دسترسی به محتوای فضای کاری ایجاد نمی‌کند. دسترسی محتوا همچنان به مالک/عضو فضای کاری، تخصیص staff یا رابطهٔ فعال آژانس نیاز دارد. غیرفعال‌کردن عضویت سازمان دسترسی سازمان را می‌بندد؛ برای لغو دسترسی مستقل فضای کاری، سیاست/تخصیص/رابطهٔ همان فضا را هم لغو کنید. مالک بدون نیاز به رکورد عضویت، مالک باقی می‌ماند. مالک سازمان و مالک فضای کاری دو مسئولیت جدا هستند.

| API | کاربرد |
| --- | --- |
| `GET/POST /api/organizations/` | سازمان‌های مالک/عضو فعال؛ ساخت سازمان با مالکیت کاربر جاری |
| `GET/PUT/PATCH /api/organizations/{id}/` | خواندن برای عضو؛ تغییر نام/سیاست فقط برای مالک یا superadmin |
| `GET/POST /api/organizations/{id}/members/` | فقط مالک یا superadmin؛ POST با `user_id` و `is_active` برای افزودن/فعال‌سازی/لغو عضویت |
| `GET/POST /api/organizations/{id}/workspaces/` | فقط فضاهای کاری مجاز کاربر؛ ساخت در سازمان برای مالک، ادمین سازمان یا superadmin |
| `GET /api/workspaces/{id}/organization_context/` | شناسهٔ سازمان و سیاست از فضای کاری مجاز؛ آژانس فقط همین context محدود را می‌بیند |

`resolve_organization_context` در [tenancy.py](../backend/social_stats/tenancy.py) ابتدا مجوز فضای کاری را بررسی و سپس سازمان را از دیتابیس می‌خواند. `organization_id` اختیاری باید با همان سازمان برابر باشد؛ ادعای سازمان از URL، payload یا token مجوز نمی‌سازد. پاسخ فضای کاری فیلد `organization` دارد؛ APIهای عمومی فضای کاری آن و فیلدهای مالکیت را فقط‌خواندنی نگه می‌دارند. ساخت معمولی فضای کاری سازمان مستقل می‌سازد؛ برای چند فضای کاری در یک سازمان از مسیر سازمان استفاده کنید. جابه‌جایی فضای کاری بین سازمان‌ها و انتقال مالک سازمان در این API ارائه نشده‌اند.

Migration `0076` برای هر فضای کاری قدیمی یک سازمان مستقل می‌سازد، فقط `owner_user` موجود را کپی می‌کند و هیچ عضوی از ایمیل، profile، staff یا رابطهٔ آژانس حدس نمی‌زند. رکوردهای بدون مالک همچنان بدون مالک می‌مانند؛ فقط superadmin می‌تواند سازمان آن‌ها را مدیریت کند. شناسه‌ها، جداول legacy و دادهٔ حساب/پست/آمار جابه‌جا نمی‌شوند. دستورهای bulk/import باید سازمان معتبر را صریح مشخص کنند؛ `Client.save()` در مسیرهای معمول سازمان را به‌صورت تراکنشی ایجاد می‌کند و تغییر tenant رکورد موجود را رد می‌کند. تغییر مستقیم FK با `QuerySet.update()` یا SQL مسیر انتقال پشتیبانی‌شده نیست.

## نقش و تأیید

- `superadmin`: مدیریت پلتفرم؛ `staff`: محدودهٔ اختصاص‌داده‌شده و مجوزهای خودش.
- `client` نام فنیِ نقش عضو فضای کاری است؛ `end_user` و `agency_member` نوع حساب‌اند.
- presetهای مالک/مدیر، مدیر شبکه اجتماعی، سردبیر، ویراستار و تحلیلگر فقط با انتخاب صریح اعمال می‌شوند.
- مجوز عمل و نیاز به تأیید جدا هستند. تأیید نمی‌تواند منع دسترسی را دور بزند.
- الزام تأیید فضای کاری/رابطهٔ آژانس حداقل اجباری است. نویسنده یا درخواست‌کنندهٔ انتشار نمی‌تواند درخواست خودش را تأیید کند.
- worker پیش از انتشار، عضویت و دسترسی فعلی به مقصد را دوباره بررسی می‌کند. زمان‌بندی به هر دو مجوز انتشار و زمان‌بندی نیاز دارد.
- ویرایش محتوای تأییدشده تأیید قبلی را باطل می‌کند. پست/صف بدون عامل قابل‌شناسایی منتشر نمی‌شود.

موتور واحد [authorization.py](../backend/social_stats/authorization.py) است. اول مرز فضای کاری/حساب و عضویت فعال، سپس مجوزهای پایه، preset سازمان/فضای کاری، استثناهای فضای کاری و در آخر استثناهای حساب بررسی می‌شود. منع صریح کاربر و سقف دسترسی آژانس/staff همچنان اعمال می‌شوند؛ مجوز حساب محدودهٔ فضای کاری را گسترش نمی‌دهد.

## مدیریت تیم

Access Management → Workspace Team. تنظیم سیاست به مالک فضای کاری، ادمین سازمان یا superadmin و عضو از قبل مجاز نیاز دارد. ادمین سازمان حق تغییر سیاست مالک یا ادمین‌ها و اعطای preset مالک/پرداخت را ندارد.

| API | کاربرد |
| --- | --- |
| `GET /api/management/role-presets/` | presetها |
| `GET /api/management/workspaces/{id}/team-policy/` | اعضا و سیاست |
| `GET/PUT /api/management/workspaces/{id}/team-policy/{user_id}/` | سیاست عضو |
| `GET/PUT/DELETE /api/management/workspaces/{id}/accounts/{account_id}/policy/{user_id}/` | استثناهای حساب |
| `GET/PUT /api/management/organizations/{agency_id}/members/{user_id}/preset/` | preset عضو سازمان؛ مالک سازمان یا superadmin |

مسیر `management/organizations/{agency_id}/.../preset/` نام legacy برای preset **عضو آژانس** است؛ شناسهٔ آن Agency است و با API جدید `/organizations/` و OrganizationMembership یکی نیست.

`PUT` نقشهٔ استثناهای همان محدوده را جایگزین می‌کند؛ کلید حذف‌شده ارث می‌برد و `false` منع صریح است. تغییرات در ActionLog ثبت می‌شوند.

## قرارداد سازگاری

در کد جدید و UI از `workspace` / «فضای کاری» استفاده کنید. APIهای `workspaces/` و `management/workspaces/` نام‌های اصلی‌اند؛ `clients/` و `management/clients/` همچنان با همان داده و کنترل دسترسی کار می‌کنند.
فیلدهای `workspace`، `workspace_id`، `workspace_ids` و `assigned_workspaces` با نام‌های قدیمی متناظر سازگارند؛ ارسال مقادیر متعارض خطاست. JSONهای آزاد بازنویسی نمی‌شوند.
مسیر UI اصلی `/admin/workspaces` و `/admin/workspace/{id}` است؛ aliasهای قدیمی و portalهای `/client/*` حفظ شده‌اند.
مدل `Client`، ستون‌های `client_id`، کدهای مجوز و جداول legacy را بدون migration جداگانه تغییر یا حذف نکنید. مرجع تبدیل: [workspace_vocabulary.py](../backend/social_stats/workspace_vocabulary.py).

## ثبت‌نام و راه‌اندازی مجموعه

ورودی اصلی `/signup` است. `/auth/end-user/signup` با حفظ query به آن هدایت می‌شود. هر دو API ثبت‌نام (`auth/signup/` و `end-user/signup/`) حساب غیرفعال و ایمیل تأیید می‌سازند؛ تا تأیید ایمیل JWT/session صادر نمی‌شود. حساب‌های جدید `end_user` هستند و ورود یا `/me` برای آن‌ها خودکار سازمان/فضای کاری نمی‌سازد. مسیر سازگاری حساب‌های legacy حفظ شده است. ورود اجتماعی جدید نیز از راه‌اندازی صریح مجموعه استفاده می‌کند.

پس از تأیید، کاربر به `/u/organizations` می‌رود: دعوت‌های ایمیل خودش را می‌بیند یا سازمان خودش را می‌سازد، برندها را اضافه می‌کند و به هر برند حساب‌های اجتماعی متصل می‌کند. هر برند فضای کاری مستقل در همان Organization است؛ ایمیل تماس برندها می‌تواند مشترک باشد و مرز دسترسی از شناسه و مالکیت می‌آید، نه ایمیل. انتخاب فضای کاری پیش‌فرض فقط از فضاهای مجاز انجام می‌شود؛ اتصال‌های شبکهٔ اجتماعی نیز از scope مجاز مسیر استفاده می‌کنند.

هیچ‌یک از این مراحل `is_staff` یا `superadmin` ایجاد نمی‌کند. Django Admin ابزار مدیر پلتفرم است.

## نقش سازمان و دعوت تیم

`OrganizationMembership.role` نقش `member` یا `admin` دارد؛ مالک واقعی همچنان `Organization.owner_user` است. ادمین سازمان می‌تواند برند بسازد و اعضای معمولی و دعوت‌های آن‌ها را مدیریت کند، اما تغییر سازمان/سیاست مشترک، پرداخت، تعیین ادمین دیگر و تغییر دسترسی مالک یا ادمین‌ها فقط برای مالک است. نقش سازمانی دسترسی خودکار به محتوای همهٔ برندها نمی‌دهد؛ مجوزهای محتوایی از نقش صریح هر برند می‌آیند.

| preset جدید | اختیار پیش‌فرض |
| --- | --- |
| `designer` — طراح / تولیدکننده محتوا | دیدن پست‌ها و ساخت پیش‌نویس؛ بدون انتشار، زمان‌بندی، تأیید، صندوق پیام یا پرداخت |
| `brand-manager` — مدیر برند | دیدن محتوا، آمار و مخاطبان، گزارش/خروجی و تأیید پست؛ بدون انتشار و پاسخ‌گویی |
| `workspace-admin` — ادمین اجرایی | عملیات اجرایی برند؛ بدون تغییر پرداخت، ساخت/هزینهٔ تبلیغات و ارسال کمپین |

preset به‌تنهایی کسی را ادمین سازمان نمی‌کند. migration فقط presetهای جدید را در صورت نبودن می‌سازد و presetهای سفارشی موجود را تغییر نمی‌دهد. presetهای `social-media-manager`، `senior-editor`، `editor` و `analyst` قبلی نیز قابل انتخاب‌اند.

| API | کاربرد |
| --- | --- |
| `GET/POST /api/organizations/{id}/invitations/` | فهرست و دعوت با `email`، `organization_role` و `workspace_grants: [{workspace_id, preset}]` |
| `DELETE /api/organizations/{id}/invitations/{invitation_id}/` | لغو دعوت در انتظار |
| `PUT /api/organizations/{id}/team/{user_id}/` | جایگزینی برندهای مجاز/نقش یا لغو عضویت و سیاست‌های همان سازمان |
| `GET /api/organization-team/invitations/` | دعوت‌های معتبر متعلق به ایمیل کاربر جاری |
| `POST /api/organization-team/invitations/{id}/accept/` | پذیرش با حساب فعال و ایمیل تأییدشدهٔ همان دعوت |
| `GET /api/organization-team/invitation/?token=…` | پیش‌نمایش محدود دعوت از پیوند ایمیل |
| `POST /api/organization-team/invitation/` | پذیرش پیوند با `{token}` و همان کنترل ایمیل |
| `POST /api/organizations/{id}/select_workspace/` | انتخاب فضای کاری مجاز با `{workspace_id}` |

توکن دعوت تصادفی است و فقط digest آن ذخیره می‌شود؛ ۷ روز اعتبار دارد و پذیرش/لغو آن یک‌بار انجام می‌شود. اختیار فعلی دعوت‌کننده هنگام پذیرش دوباره بررسی می‌شود. دعوت مجدد همان ایمیل دعوت قبلی در انتظار را لغو می‌کند. پذیرش، عضویت و سیاست‌ها را اتمیک می‌سازد و برندهای مجاز همان سازمان را جایگزین می‌کند؛ سازمان‌های دیگر تغییر نمی‌کنند. سهمیهٔ عضو هنگام پذیرش اعمال می‌شود. لغو دسترسی عضو، دعوت‌های در انتظار او و سیاست‌های همین سازمان را غیرفعال می‌کند؛ مالکیت مستقل یا رابطهٔ آژانس از این مسیر منتقل نمی‌شود.

عضو به `profile.client` متصل نمی‌شود، چون آن مسیر legacy معنای مالک دارد؛ `default_workspace` فقط انتخاب نمایشی است و با دسترسی جاری بررسی می‌شود. اعطای دسترسی آژانس از فضای کاری پیش‌فرض هم همچنان مالک واقعی می‌خواهد. تغییرات تیم در SecurityAuditLog ثبت می‌شوند.
